# Explicit primary atom scope and bounded semantic reassessment

## Incident and representation boundary

At commit `026c835`, a BSU primary obligation describing a printed label had
`applicability: null`. Canonical optional-null normalization omitted it. Local
validation accepted the representation, while independent review explicitly
judged `applicable`; exact typed alignment therefore rejected the pair. This
was not a score failure, and absence is not evidence of applicability.

The captured single-clause fixture retains original source, primary proposal
and rejected reviewer fields, with source-file hashes. Tests regenerate fresh
request identities and reference selectors; this is offline evidence, not a
reused production response or real-provider acceptance.

## New generation, historical representation and retries

`primary_generation_schema()` creates a separate model-facing projection for
NEW v3 primary proposals. Every emitted obligation must explicitly include
`force` and `applicability` from their closed enum domains. The same schema is
in the compact packet for ordinary hosts and the native decoding schema for
Codex. No value is supplied or inferred by this code.

The canonical historical-response schema and independent-review schema remain
unchanged. A retry keeps its parent's schema instead of demanding newly filled
fields across unrelated atoms. Generation guidance applies to new proposals;
the immutable-parent and named-field authorization rules take precedence on a
retry. A typed field missing in a historical proposal is never treated as a
default, and independent exact alignment still rejects disagreement.

## Authenticated scope opportunity, not a pass

After the same-candidate independent-review budget is exhausted, the complete
rejected review may authorize one fresh primary applicability proposal only if
all remaining checks are valid and all discrepancies are in `applicability`,
`target`, or `condition`. Each individual atom receives only its actually
disputed fields. The record binds the current source, quote, complete request,
candidate, rejected review, run and clause/evidence identity. Missing mappings,
bad references, changed modality, stale sources and unrelated errors do not
authorize this transition.

The new proposal may not alter actor, action, modality, quote, status, route,
reasons, classifications, obligation inventory or requirements. Existing
condition-specific label display authorization remains restricted to a
separately disputed condition and its exact source field; applicability alone
does not authorize a DOCX property change. Unknown/conflicted applicability
cannot accompany a `covered` atom in this transition or in ordinary shared
response validation. Pending/unresolved atoms can retain these explicit values.

No reviewer value is copied. The primary must re-read the source and may return
unchanged if no safe correction fits. The shared one-shot scope proposal budget
does not reset between target, condition and applicability disagreements.
Both raw and projected candidate comparisons, full local validation and a
fresh source-first independent review remain mandatory before acceptance.
Receipts explicitly retain `submission_ready=false`, independent-review
required, and no mechanical-equivalence claim.

## Offline acceptance scope

Regression cases cover the captured omission, renamed source IDs, complete and
mixed scope feedback, wrong/stale sources, duplicate/missing checks, unrelated
mapping/reference/force errors, forbidden edits and deletion, old-parent hashes,
host-neutral generation, canonical compatibility, exhausted review routing,
bounded bridge retry and rejection without publication. Genuine BSU and Word
acceptance must be reported separately from these tests.

The current retained original incident was also replayed as a complete
20-check/20-result rejected bundle: only the label atom's applicability was
named for reassessment. The fixture's clause, primary review and reviewer result
were compared directly with the original files, and all three recorded original
file hashes matched. This evidence does not make the rejected response valid.

Two read-only red-team scouts checked routing and generation integration. Their
claim that the fresh schema accepts null was rejected after observing the
actual non-empty validation error list (the helper returns errors, not a
boolean pass). Their covered/unknown counterexample was confirmed and closed
in shared response validation with a negative regression, retaining unresolved
states for pending judgments. These checks are scoped, not a whole-repository
proof or a substitute for a fresh provider run.
